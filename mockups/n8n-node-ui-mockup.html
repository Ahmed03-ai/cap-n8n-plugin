Credential screen — Basic Auth

The workflow designer enters the CAP service URL and login details once. All CAP nodes in any workflow can then reuse this credential. A "Test Connection" button calls GET /$metadata to verify credentials and discover available entity sets.

Credential screen — OAuth2

For BTP-deployed CAP services, OAuth2 client credentials flow is used. The node fetches and caches a bearer token before each request. A failed test shows a clear error so the user knows exactly what to fix.

OAuth2 token — fetched via client credentials grant, cached until expiry, refreshed automatically

Query mode — "I need a list"

Use this when you don't know which records you want yet. You can filter, sort, and paginate. Returns an array — each record becomes a separate item in n8n for the next node to process.

Read mode — "I need one specific record"

Use this when a previous step already gave you an ID. No filtering or sorting — just provide the key and get that exact record back. Returns a single object, not a list.

n8n expressions — all fields accept {{ $json.field }} to reference data from previous nodes

Create mode

Sends a POST request with the JSON body. The created record — including any server-generated fields like ID — is returned as output for the next node.

Update mode

You provide the ID of the record and only the fields you want to change. Fields you leave out are not touched. Uses PATCH, not PUT.

Delete mode

Provide the ID of the record to remove. Returns confirmation on success, or a clear "not found" error if the record doesn't exist.

Create — POST {baseUrl}/odata/v4/{service}/{entity} with JSON body
Update — PATCH {baseUrl}/odata/v4/{service}/{entity}({key}), only changed fields needed
Delete — DELETE {baseUrl}/odata/v4/{service}/{entity}({key}), returns 204 No Content on success

CAP Configuration

cap-n8n-plugin · server-side setup

No visual node UI here — this is configured in code. The mockup shows what the developer writes.
cds.requires — package.json
"cds": {
  "requires": {
    "n8n": {
      "kind": "n8n",
      "url": "http://localhost:5678",
      "auth": {
        "type": "basic",
        "user": "admin",
        "password": "env:N8N_PASSWORD"
      }
    }
  }
}
Usage in a CAP event handler
// Connect once at module level
const n8n = await cds.connect.to('n8n');

// Inside your CAP handler
this.on('submitOrder', async req => {
  const result = await n8n.start(
    'order-fulfillment',  // webhook path
    { orderId: req.data.ID }
  );
  // result.executionId → "42"
});

Error States

How errors surface — covers US 2.1 acceptance criteria on error propagation

401 Unauthorised Invalid credentials for the n8n instance. Check cds.requires.n8n.auth config or the env variable.
404 Not Found — entity Entity Books(999) does not exist. Returned as a standard CDS error to the handler.
Workflow not found No active workflow with webhook path order-fulfillment. Check the path matches exactly in n8n.
400 Bad Request OData validation error: Value for 'price' must be a number. Propagated as CDS error.
Connection refused Could not reach n8n at http://localhost:5678. Is the n8n instance running and accessible?
No retry by default n8n.start() does not retry on failure. Handle retries in the CAP handler with try/catch, or add an n8n retry node downstream.
N8nWorkflowService — provided by cap-n8n-plugin; registered via cds.connect.to('n8n')
workflowId — must match the Webhook Trigger path in n8n exactly (case-sensitive)
executionId — returned synchronously when n8n accepts the call; the workflow result itself is async unless a callback URL is used
Error propagation — per US 2.1 AC, all n8n API errors are re-thrown as standard CDS errors so CAP handlers catch them normally

Future Enhancement — Dynamic Parameter Fields

The current design uses a single JSON input for parameters. A future version could instead read the action's parameter definitions from $metadata and render individual typed input fields for each parameter — similar to how Salesforce or HubSpot nodes work in n8n. This would give non-technical users a guided form instead of a raw JSON editor, with the correct field types (text, number, dropdown) inferred automatically from the action definition.

$metadata filtering — the Action dropdown should only show Action elements from metadata, not Function elements (functions use GET, not POST)
Empty parameters — if the action takes no parameters, the field can be left blank or set to {}; the node should handle both gracefully
Return type — CAP actions can return a primitive, a complex type, an entity, or nothing (204); the output preview should reflect whatever comes back
