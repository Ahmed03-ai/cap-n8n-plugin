<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CAP caller -> execution store | Caller-provided workflow metadata becomes persisted local execution data. |
| n8n response/error -> execution DTO | External response and error data become queryable CAP-visible execution fields. |
| package model -> consuming CAP app | The plugin introduces a package-owned CDS entity that consumers compile and deploy. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure | `ExecutionStore` DTOs | mitigate | Reuse sanitizer logic and explicitly omit inputs, headers, API keys, payloads, request bodies, stack traces, and configured secret values from exposed records. |
| T-03-02 | Tampering | execution status fields | mitigate | Validate status values against the D-01 lifecycle vocabulary before writing state transitions. |
| T-03-03 | Repudiation | local versus n8n execution identity | mitigate | Always generate a plugin-owned `executionId` and store any external ID separately as `n8nExecutionId` per D-04. |
| T-03-SC | Tampering | npm installs | accept | Phase 3 adds no external packages; use existing CAP, Node, and Vitest dependencies only. |
</threat_model>
