# Technology Stack Research

**Project:** CAP n8n Integration
**Research dimension:** Stack
**Researched:** 2026-05-28
**Overall confidence:** HIGH for CAP/n8n runtime choices, MEDIUM for n8n community-node package details that may change with weekly n8n releases.

## Recommendation

Use a single npm-workspace stack on **Node.js 22.16+**, **npm lockfile v3**, **SAP CAP 9.9.x**, **n8n 2.22.x**, **Vitest**, and the official **n8n-node CLI**. Keep the CAP plugin runtime in CommonJS for this milestone because the repo is already CommonJS and CAP service implementations are currently CommonJS. Build the n8n community node in TypeScript because current n8n node scaffolding, file naming, and docs assume TypeScript node and credential files.

The most important brownfield correction is to stop relying on global tools and floating Docker images. Add local dev dependencies, pin the n8n runtime image/version, define root scripts that exercise all workspaces, and make `cap-n8n-plugin` and `cap-n8n-node` installable packages instead of placeholders.

## Runtime Versions

| Runtime | Recommended Version | Confidence | Why |
|---|---:|---|---|
| Node.js | `>=22.16 <25` | HIGH | `@sap/cds@9.9.1` requires Node `>=20`, while current `n8n@2.22.4` requires Node `>=22.16`; n8n docs also cap supported npm installs at Node 24.x. Node 22.16+ satisfies both without jumping to Node 24. |
| npm | npm 11.x with lockfile v3 | HIGH | The repo already has npm workspaces and package-lock v3. Do not introduce pnpm/yarn during this milestone. |
| SAP CAP | `@sap/cds@^9.9.1` | HIGH | CAP release docs list CAP Node.js 9.9 as the April 2026 line; live npm metadata reports `@sap/cds` latest as 9.9.1. |
| CAP CLI | `@sap/cds-dk@^9.9.1` as a root dev dependency | HIGH | CAP docs show `cds` CLI usage through `@sap/cds-dk`; make it local so CI and new machines do not depend on global installs. |
| SQLite adapter | `@cap-js/sqlite@^2.4.0` in demo/dev test scope | HIGH | Already present in the demo and current on npm. Keep it for local CAP integration tests. |
| n8n local runtime | `n8nio/n8n:2.22.4` or the matching pinned `n8n@2.22.4` | MEDIUM | n8n docs list 2.22.4 as current stable on 2026-05-28; live npm metadata confirms `n8n@2.22.4` requires Node `>=22.16`. Pin a concrete version instead of `latest`. |
| n8n node tooling | `@n8n/node-cli@0.32.1`, `@n8n/create-node@0.31.1` for scaffolding reference | MEDIUM | n8n docs call `n8n-node` the official community-node CLI. Versions are from live npm metadata. |
| Test runner | `vitest@^4.1.7` | HIGH | CAP docs explicitly recommend Vitest over Jest when using CAP's current Chai/ESM testing path. Vitest also handles JS and TS in one workspace. |

## Package and Dependency Choices

### Root Workspace

Keep the root as a private npm workspace:

```json
{
  "private": true,
  "workspaces": ["demo-app", "cap-n8n-plugin", "cap-n8n-node"],
  "engines": { "node": ">=22.16 <25", "npm": ">=11" }
}
```

Add root dev dependencies used across packages:

| Package | Version | Purpose | Confidence |
|---|---:|---|---|
| `@sap/cds-dk` | `^9.9.1` | Repo-local `cds`, `cds watch`, `cds build`, `cds env`, integration test commands | HIGH |
| `vitest` | `^4.1.7` | Workspace test runner for CAP plugin, n8n node helpers, metadata parsing, and import logic | HIGH |
| `@n8n/node-cli` | `0.32.1` | Official n8n community-node build/lint/dev workflow | MEDIUM |
| `eslint` | `9.29.0` | Peer dependency expected by `@n8n/node-cli@0.32.1` | MEDIUM |
| `typescript` | pin to the version generated by `npm create @n8n/node@latest` | n8n node compilation only | MEDIUM |

Recommended root scripts:

```json
{
  "scripts": {
    "dev:cap": "npm --workspace demo-app run watch",
    "dev:n8n": "docker compose up n8n",
    "build": "npm run build --workspaces --if-present",
    "lint": "npm run lint --workspaces --if-present",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:cap": "cross-env CDS_TEST_ENV_CHECK=1 vitest run cap-n8n-plugin demo-app",
    "test:n8n-node": "npm --workspace cap-n8n-node run lint && npm --workspace cap-n8n-node run test"
  }
}
```

Use `cross-env` only if Windows/Linux CI parity becomes painful; otherwise keep scripts plain PowerShell/GitHub Actions compatible.

### CAP Plugin Package

`cap-n8n-plugin` should be a real CAP plugin package:

| Manifest Field | Recommended Value | Why |
|---|---|---|
| `main` | `index.js` exporting public helpers/client types | Consumers should be able to `require('cap-n8n-plugin')`; current empty entry point is a packaging bug. |
| `files` | `["index.js", "cds-plugin.js", "lib", "srv", "package.json", "README.md"]` | Publish only runtime artifacts and service models. |
| `peerDependencies` | `{ "@sap/cds": "^9.9.1" }` | The host CAP app must provide CAP; the plugin should not bundle its own CAP runtime. |
| `devDependencies` | `{ "@sap/cds": "^9.9.1", "@cap-js/sqlite": "^2.4.0", "vitest": "^4.1.7" }` | Needed for package-local integration tests. |
| `engines.node` | `>=22.16 <25` | Align with workspace and n8n, even though CAP 9 itself only requires Node 20+. |
| `cds` config | Provide default `requires.n8n` kind/schema in `package.json`, not only mutation in `cds-plugin.js` | CAP plugin docs support package-level auto-configuration through a plugin package's `cds` section. |

Keep CAP plugin implementation in CommonJS for now. The value is CAP integration behavior, not a TypeScript migration. Generate CDS service models for `N8nWorkflowService` and add JSDoc typedefs if helpful, but avoid converting the CAP package to ESM until there is a concrete consumer requirement.

HTTP stack for CAP-to-n8n:

| Concern | Recommendation | Why |
|---|---|---|
| HTTP client | Node 22 global `fetch` plus `AbortController` | Already used by the prototype; CAP testing docs now rely on native Fetch. Avoid Axios unless a real missing feature appears. |
| Retry | Small internal retry wrapper around `fetch` | Requirements need retry/timeout/status classification, not a broad HTTP framework. |
| Logging | `cds.log('n8n')` | Matches CAP conventions and existing code. Do not add Pino/Winston. |
| Errors | Standard CAP errors with sanitized details | Keeps OData/CAP responses predictable and avoids leaking n8n response bodies. |

### n8n Community Node Package

The workspace folder can remain `cap-n8n-node`, but the publishable package name should be changed before release:

| Manifest Field | Recommended Value | Confidence | Why |
|---|---|---|---|
| `name` | `n8n-nodes-sap-cap` or `@<scope>/n8n-nodes-sap-cap` | HIGH | n8n community-node standards require package names to start with `n8n-nodes-` or scoped equivalent. |
| `keywords` | include `n8n-community-node-package` | HIGH | Required by n8n community-node standards. |
| `n8n.nodes` | compiled node file path(s) under `dist/nodes/...` | HIGH | n8n requires package metadata listing nodes. |
| `n8n.credentials` | compiled credential file path(s) under `dist/credentials/...` | HIGH | n8n requires package metadata listing credentials. |
| `main` | `dist/index.js` only if the scaffold generates it | MEDIUM | n8n loads from the `n8n` manifest entries; do not rely on the empty current `index.js`. |

Recommended n8n node implementation stack:

| Package | Version | Purpose | Confidence |
|---|---:|---|---|
| `n8n-workflow` | align with the local n8n 2.22.x install | Node interfaces, error types, item types | MEDIUM |
| `fast-xml-parser` | `^5.8.0` | Parse CAP OData `$metadata` for entity sets, keys, actions, and functions | MEDIUM |
| `@n8n/node-cli` | `0.32.1` | Build, lint, and run local n8n with the node loaded | MEDIUM |
| `typescript` | scaffold-pinned | Compile `.node.ts` and `.credentials.ts` files | MEDIUM |

Use n8n's programmatic-style node, not declarative routing, because CAP OData URLs vary by entity set, key shape, bound/unbound action/function metadata, and response cleanup rules. The official n8n docs say programmatic nodes use an `execute()` method that reads item data and builds requests; that matches Query, Read, Create, Update, Delete, and Action/Function operations.

For n8n HTTP calls, use `this.helpers.httpRequestWithAuthentication.call(this, 'sapCapApi', options)`. The official docs recommend that helper over passing Basic Auth directly in request options. Use `NodeApiError` and `NodeOperationError` from `n8n-workflow` for clear editor/runtime errors.

Recommended structure:

```text
cap-n8n-node/
  credentials/SapCapApi.credentials.ts
  nodes/SapCap/SapCap.node.ts
  nodes/SapCap/actions/entity/query.operation.ts
  nodes/SapCap/actions/entity/read.operation.ts
  nodes/SapCap/actions/entity/create.operation.ts
  nodes/SapCap/actions/entity/update.operation.ts
  nodes/SapCap/actions/entity/delete.operation.ts
  nodes/SapCap/actions/actionFunction/invoke.operation.ts
  nodes/SapCap/methods/loadOptions.ts
  nodes/SapCap/transport/capApi.ts
  nodes/SapCap/metadata/parseMetadata.ts
  nodes/SapCap/metadata/cache.ts
```

## Test Tooling

Use integration tests as the main quality gate, matching the existing requirements language.

### CAP Plugin Tests

| Test Area | Tooling | Recommendation |
|---|---|---|
| CAP service integration | `cds.test()` + Vitest | Start a temporary CAP app/server and verify `cds.connect.to('n8n')`, service model actions, profile config, and persistence behavior. |
| HTTP behavior | Node `http` test server + global `fetch` | Simulate n8n success, 4xx, 5xx, timeout, malformed JSON, empty body, and retryable failures without requiring a real n8n container. |
| Data reset | `cds.test().data.reset()` | Reset SQLite/in-memory state between integration cases. |
| Plugin bootstrap | `CDS_TEST_ENV_CHECK=1` | CAP docs recommend this guard to catch tests that load `cds.env` from the wrong root. |
| Demo smoke | `cds.test().in("demo-app")` | Verify the brownfield demo still starts and the existing Book create trigger can run against a fake n8n endpoint. |

Do not use Jest as the default. CAP docs explicitly recommend migrating to Vitest or using Jest's own `expect` because current Chai is ESM and Jest has compatibility friction.

### n8n Community Node Tests

| Test Area | Tooling | Recommendation |
|---|---|---|
| Node package validity | `n8n-node lint` | Required before considering the package publishable. |
| Local editor load | `n8n-node dev` | Use for manual/editor smoke testing because it starts local n8n with the node loaded. |
| Operation logic | Vitest | Extract URL building, key serialization, OData cleanup, metadata parsing, and error mapping into pure modules and test them directly. |
| Metadata discovery | Vitest + recorded `$metadata` fixture from `demo-app` | Verify EntitySet, key, action, and function extraction without starting n8n. |
| End-to-end smoke | Docker Compose n8n + local CAP demo | Keep this as a slower integration lane, not the default inner-loop test. |

Do not add Playwright for n8n editor UI testing yet. The current risk is package loadability and operation behavior; official `n8n-node dev` plus lint gives enough signal for the first robust package phase.

## Local Development Tooling

| Tool | Recommendation | Confidence |
|---|---|---|
| Docker Compose | Keep it, but pin the n8n image to `2.22.4` and persist `.n8n-data` | HIGH |
| CAP watch | Add `demo-app` script `"watch": "cds watch"` using local `@sap/cds-dk` | HIGH |
| n8n workflow fixtures | Keep `test-workflows/workflows.json`, but sanitize owner/project IDs before treating it as a test fixture | HIGH |
| Environment config | Add `.env.example` later with `N8N_BASE_URL`, `N8N_API_KEY`, `CDS_ENV`, and profile examples | HIGH |
| Hybrid testing | Use CAP `cds bind` only for real BTP/cloud service tests, not for the default local mock | MEDIUM |

Recommended profiles:

| Profile | n8n Behavior | Use |
|---|---|---|
| `[development]` | Plugin mock implementation unless explicit real credentials are supplied | Default local coding and deterministic tests. |
| `[local-n8n]` | Real `http://localhost:5678` n8n Docker runtime | Demo and workflow import/export tests. |
| `[hybrid]` | Remote n8n URL/API key from env or service binding | Local CAP against cloud n8n. |
| `[production]` | Require HTTPS base URL and credentials; fail startup if missing | BTP/cloud deployment. |

## What Not To Use

| Avoid | Reason |
|---|---|
| Node 18 | Current CAP 9 requires Node >=20 and current n8n 2.22.x requires Node >=22.16. |
| `n8nio/n8n:latest` | Weekly n8n releases can break local tests or change node tooling behavior unexpectedly. |
| Global-only `@sap/cds-dk` | Breaks CI and fresh machines; use a local dev dependency and npm scripts. |
| Jest as the default runner | CAP's current testing docs warn about Chai ESM/Jest friction and recommend Vitest. |
| Axios for normal CAP HTTP calls/tests | CAP testing moved to Fetch API and Node 22 includes global Fetch. Add Axios only if a concrete feature requires it. |
| `request`, `request-promise`, or old n8n request helpers | n8n docs say new nodes should use the modern HTTP request helpers. |
| Hand-written n8n package layout copied from old tutorials | Current n8n docs recommend `n8n-node`/`@n8n/create-node` for verified community-node structure. |
| Full TypeScript migration of `cap-n8n-plugin` now | It adds churn without improving the CAP plugin milestone. Use TypeScript only for the n8n node package. |
| A production database for the demo app | SQLite is sufficient for integration tests and the demo; production persistence is outside this stack research scope. |
| Heavy container orchestration for default tests | Mock n8n with a local HTTP server for fast integration tests; reserve Docker n8n for slower smoke tests. |

## Suggested Install Commands

Run these only when implementation starts; this research file does not modify package manifests.

```bash
npm install -D @sap/cds-dk@^9.9.1 vitest@^4.1.7
npm install -D @n8n/node-cli@0.32.1 eslint@9.29.0 --workspace cap-n8n-node
npm install fast-xml-parser@^5.8.0 --workspace cap-n8n-node
npm install -D @sap/cds@^9.9.1 @cap-js/sqlite@^2.4.0 --workspace cap-n8n-plugin
```

Use `npm create @n8n/node@latest` in a throwaway directory to inspect the current scaffold, then port the generated package metadata and structure into `cap-n8n-node`. Do not blindly replace the workspace package because the repo already has requirements, mockups, and package boundaries.

## Roadmap Implications

1. **Stack stabilization first:** Add engines, local CLI dependencies, passing workspace scripts, and pinned Docker n8n before building new behavior. This removes global-tool and floating-version noise.
2. **CAP plugin contract second:** Add package metadata, CDS service model, CommonJS implementation exports, mock service, and `cds.test()` integration coverage.
3. **n8n node scaffold third:** Convert `cap-n8n-node` into a TypeScript n8n community node package with official manifest shape, credential class, and lint/dev scripts.
4. **Cross-system integration last:** Add Docker n8n plus CAP demo smoke tests after the package-level tests are deterministic.
